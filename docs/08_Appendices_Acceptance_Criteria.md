# 1. Purpose

This document contains the final acceptance criteria, deployment checklist,
quality assurance standards, glossary, assumptions, constraints,
future enhancements, and project completion requirements.

This is the final document of the Software Requirements Specification (SRS).

Its purpose is to define exactly when the Election Management Platform can
be considered production-ready.

# 4. Election Acceptance Criteria

The platform shall simultaneously support

## Regular Election

- Eight Voting Nodes

- Independent Results

- Independent Candidates

- Independent Positions

---

## House Election

Eight Voting Nodes

Administrator assigns

- Pallava
- Pandya
- Chera
- Chola

Each house supports a configurable number of leadership positions (typically 2–3).

Each house maintains its own candidates, positions, votes, and live results.

Publishing or modifying one election must never affect the other.

# 23. Known Constraints

The initial deployment assumes

- Maximum 16 voting nodes.
- Approximately 3–5 remote live viewers.
- Single school environment.
- One active election event at a time (supporting both Regular and House elections concurrently).
- Free deployment using Cloudflare Tunnel until a custom domain is obtained.

These constraints can be expanded in future versions.

# 25. Glossary

Administrator

Person responsible for configuring and managing elections.

Teacher

Operator who records votes on the desktop application.

Student

Person whose voting preference is communicated to the teacher. Students never interact directly with the system.

Node

A desktop voting application assigned to a specific election type.

Regular Election

Main school election.

House Election

Election conducted separately for Pallava, Pandya, Chera, and Chola houses.

Heartbeat

Periodic status message sent from a desktop node to the website.

Synchronization

Automatic transfer of locally stored votes to the central server.

Configuration Package

Versioned package downloaded from the website containing candidates, positions, images, themes, and settings.

---

# 26. Assumptions

The following assumptions are made:

- All voting nodes have LAN connectivity during normal operation.
- Internet connectivity may be intermittent.
- Teachers are trained before election day.
- Administrators publish elections before voting begins.
- Desktop nodes download the latest configuration before voting starts.
- Mobile users only require read-only access.

---

# 27. Final Project Success Criteria

The Election Management Platform is considered successfully completed when:

✓ Every feature from the original desktop application has been preserved.

✓ All administration has been migrated to the website.

✓ Two election types (Regular and House) operate independently.

✓ Votes are never lost.

✓ Offline voting functions correctly.

✓ Synchronization is automatic and reliable.

✓ Live dashboards update instantly.

✓ Reports are generated accurately.

✓ Mobile users can securely monitor live results.

✓ Deployment is globally accessible using a free solution.

✓ The application is stable, secure, maintainable, and production-ready.

---

# 28. Final Project Principle

> **Accuracy, reliability, and simplicity are more important than adding unnecessary complexity.**

Every future enhancement should preserve these principles while maintaining compatibility with the architecture defined in this SRS.
